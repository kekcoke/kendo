# Kendo Orchestration Loop & Target Platform

This repository contains both the **Agentic Orchestration Loop** (the virtual software factory) and the **Target Platform** (the highly resilient, multi-instance microservice ecosystem being built).

## 🏭 The Orchestration Loop

The orchestration pipeline processes daily curriculum tasks into production-ready code through a strict, 6-phase gated loop.

0. **Phase 0:** State Initialization (`.ai/current_state.md`)
1. **Phase 1:** Architecture & Contract Design (Platform Architect)
2. **Phase 2:** Implementation & Validation (Developer + QA)
3. **Phase 3:** Observability & Validation Hardening
4. **Phase 4:** Delivery & CI/CD (DevOps / SRE)
5. **Phase 5:** Review, Merge & State Update (Reviewer)

> Phases 3 and 5 are roadmap-defined slots (see `docs/platform_roadmap.md`).
> Phase 5 currently tracks the aspirational **AI/Vector Service (FastAPI)** rollout.

## 🌐 Target Platform Architecture (Resilience & Scale)

The output of this factory is a distributed, multi-instance cloud platform designed for high availability.

* **Multi-Instance Load Balancing:** All web APIs and background workers are containerized and deployed behind a reverse proxy/load balancer (NGINX).
* **Circuit Breakers & Retries:** External API calls and database queries are wrapped in circuit breaker policies (e.g., Polly for .NET; `pybreaker` + `tenacity` for the planned FastAPI service).
* **Async Workflows:** Heavy processing and state mutations are offloaded to an Event Bus (Azure Service Bus via Rebus), allowing the API to return HTTP 202 (Accepted) immediately.
* **Graceful Degradation:** Services return standardized RFC 7807 Problem Details on failure, ensuring upstream services can parse and react to errors predictably.

## 🧭 Roadmap Status & Planned Components

The current `src/` tree is **.NET 10 only**. Components listed in `docs/platform_roadmap.md`
as planned-but-not-yet-implemented are flagged here so readers do not search the tree for code
that does not exist yet.

| Component | Status | Target Path | Roadmap Phase | Function |
|---|---|---|---|---|
| `Gateway` (.NET 10) | ✅ Implemented | `src/Gateway/` | 01 | JWT auth, rate limiting, Polly, RFC 7807 |
| `UserService` (.NET 10) | ✅ Implemented | `src/UserService/` | 01 | EF Core, pgvector, **Semantic Kernel RAG (C#)** |
| `Worker` (.NET 10) | ✅ Implemented | `src/Worker/` | 01–02 | Rebus consumer, hosted service |
| NGINX reverse proxy | ✅ Implemented | `docker-compose.yml` | 03 | Load balancing, ≥ 2 replicas per service |
| Redis | ✅ Implemented | `docker-compose.yml` | 03 | Distributed cache / session store |
| `FastAPIService` (Python) | 🟡 **Planned — not yet built** | `src/FastAPIService/` | **05** | LangChain / RAG offload, read-only pgvector access, Azure OpenAI streaming |

The FastAPI service is **aspirational architecture** referenced in the diagram below with a
dashed border. It co-exists with the .NET Semantic Kernel path: the Gateway calls both, the
.NET stack remains primary for synchronous RAG, and FastAPI is the offload target for
heavy/streaming LLM workloads. See `docs/architecture/fastapi_rag_service_spec.md` for the
spec that drives its implementation, and `docs/platform_roadmap.md` Phase 05 for milestones.
